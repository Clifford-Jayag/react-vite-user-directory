1. Why do we store the token in localStorage? What is one security risk of doing so, and what is a more secure alternative?
We store the JWT in localStorage so that the user's authentication session persists across browser refreshes and tab closures without requiring re-authentication. However, a major security risk of localStorage is its vulnerability to Cross-Site Scripting (XSS) attacks, which allow malicious client-side scripts to read and steal the stored token. A more secure alternative is storing the token inside an HttpOnly, Secure, and SameSite cookie, which prevents client-side JavaScript from accessing the token entirely. Combining short-lived access tokens held in memory with HttpOnly refresh cookies provides a robust defense against token theft.

2. What is the purpose of the AuthContext? Why not just pass the token as a prop to each component?
AuthContext provides a centralized, global state manager for user authentication status, tokens, and authorization actions across the application. Passing tokens manually as props leads to "prop drilling," forcing intermediate components to pass authentication data to deeply nested children even if they do not use it. By leveraging AuthContext alongside a custom useAuth hook, any component can directly subscribe to authentication state without cluttering parent components. This architecture keeps the React component hierarchy clean, modular, and easy to maintain as the application scales.

3. What happens on the frontend when the JWT expires? Describe the user experience you would want to implement.
When a JWT expires, subsequent API requests to protected backend endpoints fail with a 401 Unauthorized HTTP status code. If unhandled on the frontend, the UI can break or display empty states while attempting to fetch protected data. The ideal user experience involves configuring an Axios response interceptor that catches 401 errors, clears the expired token from state and localStorage, displays a notification indicating the session has expired, and automatically redirects the user to /login. Alternatively, silent token refresh logic can automatically request a new access token in the background before expiration without interrupting the user's session.

4. What is the difference between the backend's requireAuth middleware and the frontend's ProtectedRoute component? Why do we need both?
The backend's requireAuth (or authenticateToken) middleware cryptographically validates the JWT signature on incoming HTTP requests before granting access to sensitive database endpoints. Conversely, the frontend's ProtectedRoute component handles client-side UI navigation by controlling which routes are rendered based on local authentication state. We need both because client-side routing only manages visual presentation and can easily be bypassed, whereas backend validation serves as the true security perimeter protecting confidential data. Together, ProtectedRoute provides a smooth UI experience while requireAuth guarantees application security.
